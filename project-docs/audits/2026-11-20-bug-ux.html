Bugs, worst first

B1

Onboarding cannot be resumed: a paying trial starter who quits mid-tour repeats every page from the start

lowconfirmedonboarding
Impact

A customer who just paid cannot reach Home or any Skat+ feature until the whole onboarding is walked a second time. Nothing is lost or double charged, but it costs about ten extra taps right after purchase and reads as the app having forgotten the purchase. A customer who tapped Loslegen instead sees the trial pitch again, which is acceptable.

How it happens
  1. Fresh install. Swipe through the three info pages, pick a skill level, tap the trial button and confirm Apple's sheet (monthly trial starts).
  2. On the Ganz neu path the app moves to the six-page primer, then the four-page tour. Force-quit the app (or let iOS reclaim it) during the primer or tour, before the closing Quick Session ends.
  3. Relaunch. RootView shows OnboardingView again at page 0, because hasOnboarded is only written in finish().
  4. The customer who already paid has to tap through the three info pages, the skill page (answer is kept), the trial page (now 'Weiter') and then the primer and tour again before Home appears.
Where
SkatTrainer/Views/OnboardingView.swift:22SkatTrainer/Views/OnboardingView.swift:33SkatTrainer/Views/OnboardingView.swift:692SkatTrainer/RootView.swift:11
Suggested fix

Persist the onboarding stage (and page) in UserDefaults and restore it in OnboardingView.init, or write hasOnboarded as soon as the trial decision is made (purchase confirmed or Loslegen tapped) and treat the primer and tour as skippable first-run content on Home.

Evidence
@State private var page = 0
...
private enum Stage: Equatable { case pages, tour, howToPlay }
@State private var stage: Stage = .pages
...
private func finish() {
    WhatsNew.markCurrentAsBaseline()
    progress.sessionsAtOnboarding = progress.totalSessions
    progress.hasOnboarded = true
}
// RootView.swift
if hasOnboarded { HomeView() } else { OnboardingView() }

page and stage are @State only. The only persisted onboarding keys are skat.skillLevel and progress.hasOnboarded. hasOnboarded is set only in finish(), which is reached from the tour's closing session, the tour skip, or the primer skip. No scenePhase or launch code restores the stage. For a member the trial page does show 'Weiter' and startTour(), so the loop is finite, but pages 0 to 3 are always shown again.

Checked by: code read

Not proven: Needs a force quit, or iOS reclaiming the app, in the first minutes after the purchase. How often that happens is unknown, which is why this is ranked low.

B2

Restore tells a lapsed subscriber that no earlier purchase exists

lowconfirmedpurchase
Impact

A returning customer who did buy is told they never bought. They doubt the restore worked or that this is the right account, and the alert gives no way to subscribe again from it. Costs a lapsed-subscriber win-back at the exact moment they asked for their purchase.

How it happens
  1. Use an Apple Account whose Skat+ monthly or trial has expired.
  2. Install or open the app, tap Einstellungen, then Käufe wiederherstellen (or Wiederherstellen on the paywall or the trial page).
  3. RevenueCat answers with a customer record whose Skat+ entitlement is expired, so isPro stays false.
  4. The alert reads 'Für diesen Apple Account wurde kein früherer Kauf gefunden.'
Where
SkatTrainer/Views/SettingsView.swift:157SkatTrainer/Views/PaywallView.swift:491SkatTrainer/Views/OnboardingView.swift:670
Suggested fix

Have restore() return whether info.entitlements.all is non-empty. When it is and isPro is false, say 'Dein Skat+ ist abgelaufen' and offer the paywall (the Settings upgrade row or a button in the alert). Keep the current text only for an account with no entitlements at all.

Evidence
try await subscriptions.restore()
restoreMessage = subscriptions.isPro
    ? "\(Membership.name) wurde wiederhergestellt."
    : "Für diesen Apple Account wurde kein früherer Kauf gefunden."

All three restore call sites decide the message from isPro alone. SubscriptionService.restore() (SubscriptionService.swift:404) applies the CustomerInfo and keeps nothing about expired entitlements, so 'never purchased' and 'purchased, now expired' look the same. RevenueCat's CustomerInfo.entitlements.all holds expired entitlements, so the app has the data to tell them apart.

Checked by: Code reread of the three call sites and SubscriptionService.restore/apply. No test.

Not proven: Not run against a sandbox account with an expired subscription; read from the code path only.

B3

Home 'today' card and the Skat-Minute hero do not roll over at midnight while the app stays resident

lowplausibleedge
Impact

The new day's free round and the new daily Minute look unavailable until the person navigates away and back or relaunches. Streak and chips can also show the previous day's state. Nothing is lost.

How it happens
  1. Finish today's Loslegen round (or today's Skat-Minute) at 21:00, leave the app on Home (or on the Skat-Minute screen) and lock the phone.
  2. Open the app at 08:00 the next day without a cold start.
  3. Home still says 'Die heutige Runde ist geschafft' and offers no Loslegen card. The Skat-Minute screen still shows yesterday's result as 'Ergebnis ansehen' instead of 'Heutige Runde starten'.
Where
SkatTrainer/Views/HomeView.swift:193SkatTrainer/Views/SkatMinuteView.swift:6SkatTrainer/Views/SkatMinuteView.swift:43
Suggested fix

Add an @Environment(\.scenePhase) onChange (or a UIApplication.significantTimeChangeNotification receiver) in HomeView and SkatMinuteView that bumps a @State day token when the app becomes active, so the date-dependent properties are re-read.

Evidence
// HomeView.swift
if progress.quickSessionCompletedToday() { getStartedDoneCard } else { getStartedCard }
// SkatMinuteView.swift
private var today: Date { Date() }
private var todayResult: SkatMinuteResult? { store.result(for: today) }

Both values are computed inside body from Date(). Neither view observes scenePhase, significantChangeNotification (UIApplication.significantTimeChangeNotification) or a timer, so body only re-runs when an observed store publishes. Returning from the background publishes nothing by itself. Home does re-render once the ledger writes a new day key after the first navigation back to Home (onAppear calls recordMastery), which is why this is low.

Checked by: code read

Not proven: Not run on a device: whether anything else re-invalidates these bodies on foreground (for example a RevenueCat delegate callback) was not observed.

B4

A drill finished while the phone's date was set ahead freezes the streak at 1 until the real date catches up

lowconfirmedstate
Impact

A player who tested the clock, or fixed a wrong date, loses their streak counting for the length of the jump. Each session takes the clock-went-backwards early return, so neither streakCount nor lastActiveDay is written. The streak stays at 1 for as long as the date was set ahead.

How it happens
  1. Practice on consecutive days so the streak is 2 or more.
  2. In iOS Settings turn off Set Automatically for date and time and set the date one month ahead.
  3. Finish one drill. The streak resets to 1 and lastActiveDay is stored as the future day.
  4. Turn Set Automatically back on so the date is correct again.
  5. Finish a drill every day for the next 10 days.
  6. Home, Dein Fortschritt and the completion screen keep showing 1 Tag am Stück until the real date passes the future day.
Where
Shared/Services/ProgressStore.swift:117Shared/Services/ProgressStore.swift:75
Suggested fix

When the stored day is in the future by more than a day or two, treat it as a clock error: replace lastActiveDay with today's key and keep streakCount unchanged, instead of returning.

Evidence
} else if gap < 0 {
    // The clock went backwards (travel, a manual change). Keep the
    // later day so the streak is not counted twice on the way back.
    return
} // gap == 0: same day, streak unchanged

bumpStreak compares today's day key with the stored one. When the stored key is in the future, gap is negative on every call, so the function returns before it writes lastActiveDay or streakCount. Nothing ever lowers a future stored day. Small backward moves from travel correct themselves in a day, but a large forward jump does not. currentStreak(now:) also returns the frozen streakCount, because its gap is below 1.

Checked by: SkatTrainerTests/SkatMinuteTests.swift class TimeStateProofTests, testStreakNeverGrowsAfterClockWasSetAheadThenRestored (written in the scratch clone, not run). It expects a streak of at least 10 after 10 daily sessions and should fail with the streak frozen at 1.

Not proven: The gh-sim test run queued for more than 40 minutes and did not start, so the trace was not executed. Whether a real customer sets the date ahead is rare and not observed.
